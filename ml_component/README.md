# רכיב חכם - ניתוח וניהול תקציבי חכם למערכת RupResearch

רכיב זה הוא "הרכיב החכם" (Smart Component) שנבנה כחלק ממערכת ניהול
המחקר RupResearch, כדי להגיש כפרויקט מסכם בקורס **"היבטים מעשיים
בלמידת מכונה"**. הרכיב כתוב בפייתון, מתחבר ל-DB החיה של המערכת
(SQL Server), ומיישם את כל הנושאים שנלמדו בקורס - מסטטיסטיקה
תיאורית ועד Machine Learning מתקדם (Supervised + Unsupervised).

## רעיון כללי

מערכת RupResearch מנהלת פרויקטי מחקר, תקציבים ובקשות תשלום.
לאורך השנה, חוקרים מגישים בקשות תשלום (Research Payment Requests)
שמאושרות/נדחות ע"י מנהל הקרן, וכל פרויקט מתנהל לפי תקציב כולל
(`total_budget`) ולוח זמנים.

הרכיב החכם מנתח את הדאטה הזו ומספק **4 יכולות חכמות**, שמהוות
ביחד מודול "ניתוח וניהול תקציבי חכם":

| # | מודול | סוג למידה | שאלה עסקית |
|---|-------|-----------|------------|
| 1 | חיזוי אישור/דחיית בקשת תשלום | Classification | האם בקשת תשלום חדשה צפויה להיות מאושרת? |
| 2 | תחזית סכום בקשת תשלום | Regression | מה הסכום הצפוי של בקשת תשלום עתידית? |
| 3 | פילוח פרויקטים לפי דפוס הוצאות | Clustering | אילו פרויקטים מתנהגים בצורה דומה תקציבית (חסכוניים / "שורפים תקציב")? |
| 4 | חיזוי סיכון חריגת תקציב | Classification | האם אישור בקשה מסוימת עלול לגרום לפרויקט "לשרוף" תקציב מהר מהקצב הסביר? |

כל המודולים **מתחברים ל-DB החי** ושואבים נתונים עדכניים בכל הרצה -
כך שכאשר מתווספות בקשות תשלום חדשות או קטגוריות חדשות, ניתן
להריץ מחדש את הרכיב והמודלים יתאמנו מחדש על הדאטה המעודכן (אין
"רשימת קטגוריות קשיחה" מוטבעת בקוד).

## מבנה הפרויקט

```
ml_component/
├── config.py                  # פרטי חיבור ל-DB
├── db.py                       # שליפת נתונים מה-DB (payment_requests, projects)
├── data_prep.py                # צנרת הכנת הדאטה (Section 10)
├── exploratory_analysis.py     # מודול 0: סטטיסטיקה תיאורית וויזואליזציה (Section 2-3)
├── approval_classifier.py      # מודול 1: חיזוי אישור/דחייה (Classification)
├── expense_forecast.py         # מודול 2: תחזית סכום בקשה (Regression)
├── project_clustering.py       # מודול 3: פילוח פרויקטים (Clustering)
├── budget_risk_classifier.py   # מודול 4: חיזוי סיכון חריגת תקציב (Classification)
├── ml_insights.py               # נקרא ע"י השרת (C#) - מחזיר JSON חכם ל-UI (ראו פרק "שילוב ב-UI")
├── main.py                      # סקריפט מרכזי שמריץ הכל ברצף
├── requirements.txt             # ספריות פייתון נדרשות
└── output/                       # כל הגרפים שנוצרים (PNG)
```

```bash
py -m pip install -r requirements.txt
py main.py
```

(במידה ויש בעיית קידוד בעברית בקונסול ב-PowerShell, יש להריץ קודם

ניתן גם להריץ כל מודול בנפרד, לדוגמה:


## הכנת הדאטה (`data_prep.py`) - Section 10

המקור: טבלאות `research_payment_requests` ו-`research_projects`
(נשלפות ע"י `db.py` בעזרת `pyodbc`, JOIN בין הטבלאות).

נתוני המקור הגולמיים: **137 בקשות תשלום** ו-**21 פרויקטים**.

צנרת ההכנה (`build_payment_requests_dataset`) מיישמת את כל
השלבים שנלמדו ב-Section 10:

1. **Quality Check & Cleaning** (`clean_payment_requests`) - הסרת
   שורות עם ערכים חסרים קריטיים (סכום, תאריך, פרויקט) והסרת כפילויות.
   לאחר הניקוי: **137 → 124 שורות**.

2. **זיהוי חריגים (Outlier Detection)** (`detect_amount_outliers`) -
   שיטת IQR (Interquartile Range): כל ערך מעל
   `Q3 + 1.5*IQR` או מתחת ל-`Q1 - 1.5*IQR` מסומן כ-`is_amount_outlier`.
   נמצאו **23 בקשות תשלום חריגות מתוך 124** (כ-18.5%).

3. **פירוק תאריכים (Date Decomposition)** (`map_dates`) - חילוץ
   `request_month`, `days_to_due` (ימים עד מועד היעד של הפרויקט),
   ו-`project_progress_at_request` (איזה אחוז מתקופת הפרויקט עבר
   במועד הגשת הבקשה - 0 עד 1).

4. **Feature Engineering** (`engineer_features`) -
   - `approved_label`: 1 = מאושר, 0 = נדחה, NaN = ממתין להחלטה (לא
     נכלל באימון הקלאסיפיקציה).
   - `amount_to_budget_ratio`: יחס בין סכום הבקשה לתקציב הכולל
     של הפרויקט.
   - `log_amount = log(1 + requested_amount)` - **Log Transformation**
     לטיפול בהתפלגות מוטה-ימינה (Right-Skewed) של סכומי כסף.
   - `has_due_date`: דגל בינארי אם לפרויקט יש מועד יעד מוגדר.

5. **Encoding** (`encode_categoricals`) - **One-Hot Encoding** למשתנה
   הקטגוריאלי `category_name` (קטגוריית בקשת התשלום), כדי שהמודלים
   יוכלו להשתמש בו. שיטה זו אוטומטית - אם תתווסף קטגוריה חדשה ל-DB,
   היא תיכנס לקידוד בהרצה הבאה ללא שינוי קוד.

6. **Scaling** (`scale_numeric`) - **Standardization** (Z-score)
   למשתנים נומריים בסדרי גודל גדולים (כמו `total_budget`), משמש
   במודולים של Logistic Regression ו-K-Means (Section 10.5.2).

## מודול 1: חיזוי אישור/דחיית בקשת תשלום (`approval_classifier.py`)

**Supervised Learning - Classification**. המטרה: לחזות, בהינתן
מאפייני בקשת תשלום (סכום, קטגוריה, יחס לתקציב, שלב הפרויקט וכו'),
האם היא תאושר (`approved_label = 1`) או תידחה (`= 0`).

- מודלים: **Logistic Regression**, **Decision Tree**, **Random Forest**.
- כל המודלים מוגדרים עם `class_weight="balanced"` - מכיוון
  שהדאטה **מוטה (Skewed Classes)**: 90 בקשות מאושרות לעומת רק 11
  בקשות שנדחו. זה מדגים בדיוק את הנושא של "Skewed Classes" מתוך
  הרצאת Classification Evaluation - בלי איזון המודל היה "לומד"
  פשוט לחזות "מאושר" כל הזמן ולקבל Accuracy גבוה אך חסר תועלת.
- הערכה: Confusion Matrix, Accuracy, Precision, Recall, F1, ROC/AUC,
  Cross-Validation (5-fold).
- **תוצאות**: Accuracy ≈ 0.77-0.81, אך AUC ≈ 0.42-0.50 - כלומר
  המודל מתקשה להפריד אמיתית בין מאושר לנדחה. זו תוצאה כנה
  שמדגימה מגבלה אמיתית: עם רק 11 דחיות בדאטה, אין מספיק מידע
  סטטיסטי כדי ללמוד דפוס מהימן - **מסקנה חשובה למצגת**: איכות
  התחזית תלויה בכמות הדאטה ההיסטורית, וככל שתצטבר יותר היסטוריה
  במערכת, ניתן לצפות לשיפור.

פלטים: 4 גרפים (Confusion Matrices, Feature Importance, ROC Curves
וכו') בתיקיית `output/`.

## מודול 2: תחזית סכום בקשת תשלום עתידית (`expense_forecast.py`)

**Supervised Learning - Regression**. המטרה: לחזות את הסכום
הכספי (`requested_amount`) של בקשת תשלום, על בסיס קטגוריה,
תקציב הפרויקט, שלב הפרויקט וכו'.

- המודל חוזה את `log(1 + requested_amount)` ולא את הסכום הגולמי
  - כדי להתמודד עם ה-Right Skew של נתוני כסף (Log Transformation,
    Section 10) - ולבסוף ממיר חזרה לשקלים (`expm1`) למדידת השגיאה
    האמיתית.
- **נמנעת דליפת מידע (Data Leakage)**: `amount_to_budget_ratio`
  *לא* נכלל בתכונות, כי הוא מחושב ישירות מהמשתנה שאנו מנסים לחזות.
- מודלים: **Linear Regression**, **Random Forest Regressor**.
- מדדי הערכה: **MAE, MSE, RMSE** (Section 3 - Linear Regression).
- **תוצאות**: Linear Regression נתן R² שלילי (-0.711) - סימן
  שהקשרים בין התכונות לסכום אינם לינאריים. Random Forest שיפר
  משמעותית ל-R² = 0.184 - מדגים כיצד מודלים non-linear מתאימים
  יותר לדאטה פיננסי מורכב, וגם שעדיין יש מקום לשיפור עם עוד דאטה
  ותכונות.

פלטים: 2 גרפים (Actual vs Predicted, Feature Importance).

## מודול 3: פילוח פרויקטים לפי דפוס הוצאות (`project_clustering.py`)

**Unsupervised Learning - Clustering**. לכל פרויקט מחושבים
מאפיינים מצרפיים (Aggregated Features): תקציב כולל, מספר בקשות,
סכום מבוקש כולל, ממוצע בקשה, מספר קטגוריות, מספר חריגים, סכום
שאושר, אחוז אישורים, ושיעור ניצול תקציב (`budget_utilization`).

- **Scaling**: Standardization לפני clustering (חיוני לאלגוריתמים
  מבוססי-מרחק).
- **K-Means** עם **Elbow Method** לבחירת מספר הקבוצות (K).
- **Hierarchical Clustering** עם **Dendrogram** (Average Linkage).
- ויזואליזציה דו-מימדית של הקבוצות בעזרת **PCA**.
- **תוצאות**: עם K=3 זוהו 3 קבוצות התנהגות. בלט במיוחד **פרויקט 24**,
  שהופיע כקבוצה נפרדת עם `budget_utilization ≈ 12.70` - כלומר
  אישר בקשות תשלום בסכום **כ-12.7 פעמים מהתקציב המוגדר לו**!
  זהו ממצא קריטי מבחינה ניהולית - הצבעה ברורה על פרויקט שדורש
  התערבות מנהלתית מיידית, וממחיש איך Clustering חושף "חריגים
  ברמת הפרויקט" שלא נראים מניתוח שורה-בשורה.

פלטים: `clustering_elbow.png`, `clustering_kmeans_pca.png`,
`clustering_dendrogram.png`, `clustering_hierarchical_pca.png`.

## מודול 4: חיזוי סיכון חריגת תקציב (`budget_risk_classifier.py`)

**Supervised Learning - Classification** עם **תווית הנדסית
(Engineered Label)**: מכיוון שב-DB אין שדה ישיר של "חריגת תקציב",
התווית מחושבת לפי היגיון עסקי:

```
spend_ratio = (סכום שאושר עד כה + סכום הבקשה הנוכחית) / תקציב כולל
time_ratio  = החלק היחסי שעבר מתקופת הפרויקט

risk = 1   אם   spend_ratio > time_ratio * 1.2
risk = 0   אחרת
```

כלומר: אם אישור הבקשה הנוכחית יגרום לפרויקט "לבזבז" תקציב בקצב
מהיר ב-20% או יותר מקצב הזמן שעבר - מסומן כ"בקשה בסיכון".

- מודלים: **Logistic Regression** (עם **Standardization** למשתנים
  הנומריים, Section 10.5.2 - נדרש לפתרון Convergence Warning),
  **Decision Tree**, **Random Forest** - כולם עם
  `class_weight="balanced"`.
- הערכה: Confusion Matrix, Accuracy, Precision, Recall, F1, AUC,
  Cross-Validation.
- **תוצאות**: **Random Forest** השיג את הביצועים הטובים ביותר -
  **Accuracy = 0.921, AUC = 0.966** - תוצאה חזקה מאוד, ומראה שניתן
  לזהות בקשות "מסוכנות תקציבית" בצורה אמינה לפני אישורן, ולתת
  התראה מוקדמת למנהל הקרן.

פלטים: `budget_risk_confusion_matrices.png`,
`budget_risk_feature_importance.png`.

## שילוב חי ב-UI (`ml_insights.py`)

בנוסף לניתוחים והגרפים שמוצגים במצגת, **כל ארבעת המודלים הסטטיסטיים
מהרכיב מחוברים בפועל למערכת החיה** ומחליפים/מעצימים פיצ'רים קיימים:

- **מודול 4 (חיזוי סיכון חריגת תקציב - Random Forest)** מחליף את
  לוגיקת "המלצות להעברת תקציב" בין פרויקטים. במקום סף קשיח של
  burn rate, כל פרויקט מקבל `risk_score` (הסתברות שהמודל נותן
  לכך שהבקשה הבאה בו "תשרוף" תקציב מהר מקצב הזמן). פרויקט עם
  ציון סיכון נמוך מוצע כ"תורם" תקציב, ופרויקט עם ציון גבוה (או
  מאזן שלילי) מוצע כ"מקבל".

- **מודול 3 (פילוח פרויקטים - K-Means)** מחליף את "קיבוץ פרויקטים
  לפי תקציב והתנהגות פיננסית" שהיה מבוסס על טווחי תקציב/קצב הוצאה
  קשיחים. כעת הקיבוץ מתבצע ע"י K-Means בפועל, וכל קבוצה מקבלת
  תווית ("פרופיל חסכוני" / "פרופיל תקין" / "פרופיל בסיכון - שריפת
  תקציב מהירה") הנקבעת אוטומטית לפי דירוג ניצול התקציב הממוצע
  בקבוצה.

- **מודול 1 (חיזוי אישור/דחיית בקשת תשלום - Random Forest)** מוצג
  בעמוד "אישורים ממתינים" (`ApprovalsPage.jsx`). על כל בקשת תשלום
  שמחכה לאישור מחושבת הסתברות אישור (`approval_probability`); בקשות
  עם הסתברות נמוכה מסומנות בתג "מומלץ לבדוק בקפידה" כדי לעזור
  למאשר לתעדף את הבדיקה.

- **מודול 2 (תחזית סכום בקשת תשלום - Random Forest Regressor)**
  מוצג גם הוא ב"אישורים ממתינים" - לכל בקשה ממתינה מחושב סכום צפוי
  (`expected_amount`) בהתבסס על דפוסי בקשות עבר דומות. אם הסכום
  המבוקש חורג משמעותית (≥×1.5) מהצפוי, הבקשה מסומנת בתג "סכום חריג"
  עם הסכום הצפוי לצדו.

**זרימת הנתונים**: `ml_insights.py` מאמן את ארבעת המודלים מול ה-DB
החי, ומחזיר JSON יחיד ל-stdout (`{"projects": {...}, "clusters":
{...}, "pending_requests": {...}}`). שרת ה-C# מריץ אותו כ-subprocess
מתוך `ProjectsController.GetMlInsights` (`GET /api/projects/ml-insights`),
עם cache של 10 דקות (`IMemoryCache`) כדי שלא יאומנו מודלים מחדש
בכל בקשה. ה-React (`ComparisonPage.jsx`) קורא ל-endpoint הזה ומשתמש
בתוצאות בפונקציות `buildClusterGroups` (קיבוץ) ו-
`buildTransferRecommendations` (המלצות העברה), ו-`ApprovalsPage.jsx`
משתמש ב-`pending_requests` כדי להציג תגי תובנה (`MlInsightBadge`)
על כרטיסי הבקשות הממתינות.

## מסקנות מרכזיות (לטובת המצגת)

1. **הדאטה הפיננסי מוטה מאוד (Right-Skewed)** - רוב הבקשות
   בסכומים קטנים, אך כמה בקשות חריגות מאוד מטות את הממוצע
   (ממוצע 9,326 ש"ח לעומת חציון 205 ש"ח). Log Transformation
   חיוני לעבודה עם דאטה כזה.

2. **Skewed Classes** - בעיית האישור/דחייה מוטה (90 מול 11),
   מה שמצריך `class_weight="balanced"` ומדגים מדויק את הנושא
   שנלמד בהרצאת Classification Evaluation. ה-AUC הנמוך (~0.5)
   הוא תוצאה כנה - לא כל בעיה ניתנת לפתרון מושלם עם דאטה מוגבל.

3. **Clustering חושף חריגים ברמת פרויקט** שלא נראים בניתוח
   שורה-בשורה - פרויקט 24 עם ניצול תקציב של פי 12.7 מהמוגדר הוא
   ממצא קריטי לפעולה.

4. **התווית ההנדסית לחריגת תקציב** (מבוססת על קצב הוצאה מול קצב
   זמן) הניבה את התוצאה החזקה ביותר במערכת (AUC=0.966) - מדגימה
   שכאשר מגדירים בעיית Classification נכון ומקושרת היטב להיגיון
   העסקי, אפשר להגיע לתוצאות שמספקות ערך אמיתי, גם עם דאטה
   מוגבל בגודלו.

5. **כל הרכיב גנרי ומתעדכן** - אין רשימות קטגוריות קשיחות, אין
   הנחות על מספר פרויקטים קבוע. בכל הרצה הרכיב שואב את הדאטה
   המעודכן מה-DB ומאמן את המודלים מחדש - כך שהוא ימשיך לפעול
   ולהשתפר ככל שתצטבר יותר היסטוריה במערכת.
